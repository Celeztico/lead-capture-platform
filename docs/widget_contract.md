# Widget Contract

## 1. Purpose and status

This document defines the browser-facing contract between the Lead-Capture Platform backend, its embeddable JavaScript widget, and the customer website that hosts it.

It specifies how a customer embeds the widget, how the widget retrieves public configuration, how form submissions are sent, and how browser security, caching, validation and error handling should behave.

> **Contract status:** This is the initial design contract. The embed URL, JavaScript API, configuration schema, headers and response formats must be checked against the actual widget and FastAPI implementation before being treated as released behavior.

## 2. Design goals

The widget should:

- Be embeddable on a customer website with a small script snippet.
- Load its JavaScript from the Lead-Capture Platform rather than requiring customers to copy application source.
- Identify the configured widget using a public widget identifier.
- Retrieve only public-safe configuration.
- Render supported fields and submit values to the public API.
- Provide accessible validation, loading, success and error states.
- Work when the customer website and API use different origins.
- Avoid exposing platform secrets or privileged management credentials.
- Fail gracefully when configuration or submission requests cannot complete.

The customer website, browser environment and all visitor-provided values are outside the platform's trust boundary.

## 3. Embedding the widget

### 3.1 Proposed embed snippet

The initial integration uses a script tag and a container element:

```html
<div
  id="lead-capture-widget"
  data-widget-id="PUBLIC_WIDGET_ID"
></div>

<script
  src="https://api.example.com/widget/v1/widget.1.js"
  defer
></script>
```

Replace `PUBLIC_WIDGET_ID` with the widget's public identifier and `https://api.example.com` with the deployed public base URL.

The exact snippet is a proposed contract. Keep it consistent with the asset URL and initialization behavior implemented by the widget.

### 3.2 Script-loading behavior

The widget script should:

1. Load without blocking the customer page's initial HTML parsing (`defer` is recommended for the snippet above).
2. Find one or more supported container elements.
3. Read each container's public widget ID.
4. Fetch public configuration from the platform API.
5. Render the form only after a valid configuration is received.
6. Display a non-sensitive loading or error state if initialization fails.
7. Avoid initializing the same container multiple times.
8. Avoid overwriting unrelated customer-page content.
9. Avoid exposing secrets or privileged API credentials in the browser.

If multiple widgets per page are supported, each container must be initialized independently and failures in one instance should not break the others. If only one widget per page is supported initially, document and enforce that limitation.

### 3.3 Customer integration responsibilities

The customer must:
- Use the public widget ID and the supported embed snippet.
- Allow the browser to load the widget asset and call the API under the site's applicable content-security policy.
- Avoid modifying the widget's internal DOM or relying on undocumented CSS classes.
- Ensure the page's own CSS does not unintentionally make the form unusable.
- Avoid placing confidential visitor information in the widget identifier or URL.

The platform must document any required `script-src`, `connect-src` or other Content Security Policy directives when the deployment origins are known.

## 4. Public widget identifier

The embed snippet uses a `public_widget_id`.

Rules:
- It identifies which public widget configuration to retrieve.
- It is intentionally visible to browsers and visitors.
- It is not a password, API key, session token or proof of authorization.
- It must not permit widget editing, submission listing, analytics access or other management actions.
- The backend must resolve the identifier to a stored widget and verify that the widget is eligible for public use.
- Unknown, disabled or archived widgets must not return active form configuration or accept new submissions.

A public ID should be generated by the server and remain stable for the widget's lifetime unless the product explicitly supports rotating it.

## 5. Configuration contract

### 5.1 Public configuration endpoint

Proposed endpoint:

```http
GET /public/v1/widgets/{public_widget_id}/config
```

No platform user authentication is required. The response must contain only the information necessary to render the widget.

### 5.2 Example configuration response

```json
{
  "public_widget_id": "c5f63c35-7df1-4d0b-a3fd-0c7f0e0c4b0a",
  "status": "active",
  "config_version": 3,
  "configuration": {
    "title": "Contact us",
    "description": "Send us a message and our team will get back to you.",
    "submit_label": "Send message",
    "success_message": "Thanks. Your message has been received.",
    "fields": [
      {
        "name": "name",
        "type": "text",
        "label": "Your name",
        "required": true,
        "placeholder": "Enter your name"
      },
      {
        "name": "email",
        "type": "email",
        "label": "Email address",
        "required": true,
        "placeholder": "you@example.com"
      },
      {
        "name": "message",
        "type": "textarea",
        "label": "How can we help?",
        "required": true,
        "placeholder": "Write your message"
      }
    ]
  }
}
```

This example is illustrative. The actual response schema must match the Pydantic response model and supported renderer.

### 5.3 Configuration properties

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `public_widget_id` | string | Yes | Public identifier for this widget |
| `status` | string | Yes | Public lifecycle status; only `active` is renderable |
| `config_version` | integer | Recommended | Monotonically increasing version for cache invalidation |
| `configuration.title` | string | Yes | Form heading |
| `configuration.description` | string | No | Optional explanatory text |
| `configuration.submit_label` | string | Yes | Submit button label |
| `configuration.success_message` | string | Yes | Message shown after successful submission |
| `configuration.fields` | array | Yes | Ordered list of supported field definitions |

Each field definition may contain:

| Property | Type | Required | Meaning |
|---|---|---:|---|
| `name` | string | Yes | Stable payload key; unique within the widget |
| `type` | string | Yes | Supported input type |
| `label` | string | Yes | Visible field label |
| `required` | boolean | Yes | Whether a value must be supplied |
| `placeholder` | string | No | Optional input hint |

Supported initial field types should be deliberately small, for example `text`, `email` and `textarea`. Add types such as `tel`, `select` or consent checkboxes only when both rendering and server-side validation support them.

### 5.4 Configuration validation and safety

- Reject unsupported field types and malformed configuration before saving it.
- Field names must be unique and must follow a documented naming convention.
- Bound the number of fields and the length of labels, placeholders and messages.
- Render labels and messages as text, not executable HTML.
- Do not evaluate configuration values as JavaScript or inject them as raw HTML.
- Do not return private workspace data, secrets, provider credentials, internal authorization state or unrelated submissions.
- Treat the configuration response as untrusted data in the browser and handle unexpected values safely.
- The backend must validate submitted values against the current stored configuration; it must not rely on the browser having used a particular configuration.

Exact limits should be chosen in implementation configuration and reflected in tests.

## 6. Submission contract

### 6.1 Endpoint and request

Proposed endpoint:

```http
POST /public/v1/widgets/{public_widget_id}/submissions
Content-Type: application/json
Origin: https://customer.example
```

The `Origin` header is generally supplied by browsers. It may be absent in some clients and can be forged outside browser enforcement, so it must not be treated as authentication.

Example request body:

```json
{
  "data": {
    "name": "Taylor Example",
    "email": "taylor@example.com",
    "message": "Please contact me about your service."
  }
}
```

Contract rules:
- `data` contains only supported fields configured for this widget.
- The visitor must not supply authoritative `workspace_id`, internal `widget_id`, creation timestamps, enrichment results or notification status.
- The backend resolves the public widget ID, derives its workspace, validates the widget's state, validates and normalizes field values, applies abuse controls, and persists the accepted submission.
- Request size, field count and individual field lengths must be bounded.
- The server is the authority for validation even if the widget performs client-side checks.

### 6.2 Successful response

For a newly persisted submission, the proposed response is `201 Created`:

```json
{
  "id": "0e1b1a0b-c4c4-4d66-9b5e-4f3a04c65e16",
  "status": "accepted",
  "message": "Your submission has been received."
}
```

The response should reveal only the information the visitor needs. Do not return the full stored submission or internal workspace details.

The widget should display the configured success message only after receiving a response that the API contract defines as successful. It should clear or preserve form values according to a consistent UX policy, and avoid automatically resubmitting a successful form.

### 6.3 Submission errors

The widget should map documented API errors to understandable messages.

| HTTP status / code | Meaning | Widget behavior |
|---|---|---|
| `400` / `422` validation error | Submitted data is invalid | Show field-specific errors when safe details are available; otherwise show a general validation message |
| `404` unknown widget | Widget cannot be found or is no longer public | Show a generic unavailable message; do not reveal private workspace information |
| `409` idempotency conflict, if supported | A retry key was reused with different input | Avoid retrying unchanged key/payload combinations blindly; show a recoverable error |
| `413` payload too large | Request exceeds server limits | Ask the visitor to shorten the input |
| `415` unsupported media type | Request format is unsupported | Treat as an integration/configuration error |
| `429` rate limited | Too many requests | Show a calm retry-later message and respect `Retry-After` if present |
| `5xx` server error | The request could not be completed or its outcome is uncertain | Show a retry option without falsely claiming the submission was lost |

The exact API error envelope is defined in `api_contracts.md`. The widget must not display stack traces, raw database errors or provider exception messages.

### 6.4 Network failures and uncertain outcomes

If the browser times out or loses its connection, it may not know whether the server stored the submission. Avoid aggressive automatic retries that could create duplicate leads.

If idempotency is implemented:
- Generate or retain an idempotency key for the logical submission attempt.
- Reuse that key only when retrying the same payload.
- Do not reuse a key for edited form data.
- Follow the API's documented replay and conflict behavior.

If idempotency is not implemented, the widget should tell the visitor that the result could not be confirmed and let them decide whether to retry. The platform must not claim duplicate prevention without a tested implementation.

## 7. Client-side validation and accessible rendering

Client-side validation exists to help visitors complete the form; it is not a security boundary.

Before submission, the widget should:
- Check required fields.
- Apply basic type-appropriate checks, such as a reasonable email syntax check.
- Prevent duplicate button clicks while a request is in progress.
- Show errors next to relevant fields when possible.
- Preserve user input when a recoverable request error occurs.
- Set a clear loading state while the request is pending.
- Restore the submit button after a failed request.
- Display a success state only after confirmed success.

Accessibility expectations:
- Associate every visible label with its input.
- Mark required fields programmatically as well as visually.
- Expose validation messages to assistive technology.
- Manage keyboard focus sensibly when errors occur.
- Use semantic form controls and buttons.
- Ensure the widget remains usable at narrow viewport widths and with keyboard navigation.

Never rely on client validation to protect the API from malformed, malicious or oversized input.

## 8. Cross-origin behavior and CORS

The widget is designed to run on customer websites whose origins usually differ from the platform API.

The backend should:
- Configure CORS for the public configuration and submission endpoints as required by browser requests.
- Support preflight `OPTIONS` requests when the browser's request requires them.
- Allow only the methods and headers the widget needs.
- Avoid reflecting arbitrary origins with credentials enabled.
- Decide whether allowed origins are global, configured per widget, or both.
- Document the policy for missing or opaque origins.

The browser may send `Origin` and preflight headers such as `Access-Control-Request-Method` and `Access-Control-Request-Headers`. The server's response must match the selected CORS policy.

**CORS is not authentication or abuse protection.** Non-browser clients can call public endpoints directly. Server-side validation, rate limiting and spam prevention remain necessary even when an origin is allowlisted.

Cross-origin behavior must be tested from a separate local test page or test origin, including preflight and rejected-origin cases.

## 9. Caching and versioning

### 9.1 JavaScript asset

Proposed asset path:

```http
GET /widget/v1/widget.{version}.js
```

Use versioned URLs so an immutable asset URL always refers to the same content.

For a content-stable, versioned asset, a suitable policy may be:

```http
Cache-Control: public, max-age=31536000, immutable
Content-Type: application/javascript; charset=utf-8
```

This header is an example, not a mandatory value. Use long-lived immutable caching only when the URL changes whenever the asset content changes. If the URL is mutable, use a shorter TTL or revalidation.

### 9.2 Public configuration

The configuration endpoint changes when a workspace edits a widget, so its cache policy must account for freshness.

Possible mechanisms include:
- `ETag` and conditional requests using `If-None-Match`.
- `Last-Modified` and conditional requests, if useful.
- A short `Cache-Control: public, max-age=...` TTL.
- Versioned configuration URLs or version-aware cache keys based on `config_version`.

Select a policy and test it. Do not combine long-lived caching with a mutable URL unless invalidation is reliable.

### 9.3 Cache correctness

- Cache keys must include the public widget identifier and any version dimension that changes the response.
- Never serve one widget's configuration for another widget.
- Do not publicly cache authenticated management responses.
- A configuration update must advance the version or invalidate the relevant cache according to the selected policy.
- Unknown, disabled and archived widgets must not remain publicly renderable indefinitely due to stale cache entries.
- Document how CDN, reverse-proxy and browser caches interact if such layers are introduced.

## 10. Failure and resilience expectations

- If the JavaScript asset fails to load, the customer page should continue to function; the widget may be absent, but it must not break unrelated page behavior.
- If configuration retrieval fails, show a generic unavailable state and avoid rendering an unsafe or partial form.
- If a submission is rejected before persistence, show the appropriate validation or retry message.
- If submission persistence succeeds but geolocation, email or webhook processing fails, the visitor should still receive the documented successful submission result.
- If the server returns a rate-limit response, avoid immediate retry loops.
- Bound network timeouts and avoid infinite retries.
- Do not log the full form body in browser console output or server logs.

## 11. Compatibility and change policy

- Keep the public configuration schema and submission payload backward-compatible within the current API version where practical.
- Add optional configuration fields only when older widget scripts safely ignore unknown properties.
- Do not rename or change the meaning of a field without a compatibility plan.
- Version the JavaScript asset separately from the public API contract if their release cycles differ.
- Test the current widget script against the supported configuration and submission API versions.
- Document any minimum browser support or required browser features when chosen.
- Update this file whenever the embed snippet, public endpoints, configuration fields, CORS policy, cache behavior or error handling changes.
